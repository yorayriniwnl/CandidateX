# CandidateX SaaS Commercial Readiness Audit

**Audit date:** 2026-09-23  
**Current checkout:** `main` at `aebee8e` (privacy fixture cleanup), with other frontend and hardening changes uncommitted  
**Decision:** **Not ready for general company production or live candidate data.** The evidence review workflow is a credible demo, but authentication, tenant authorization, operational data lifecycle, and hiring-use controls are not implemented end to end.

## Scope and evidence

Reviewed the current checkout's frontend, FastAPI entrypoints and routers, SQLAlchemy models and repository queries, local Docker configuration, environment defaults, CI workflow, and existing tests. The two task threads are now idle. Their latest branch heads are `codex/backend-hardening` (`de1aa35`) and `codex/candidatex-evidence-os` (`a456eb8`); their histories are not integrated into local `main`. The frontend and backend task branches share a base, but their browser-test changes conflict in `apps/web/tests/live-analysis.spec.ts`. Local `main` (`aebee8e`, parent `ed5a02d`) has no common Git ancestor with `origin/main` (`baa559f`), and its worktree still contains uncommitted frontend and hardening changes. The scoped privacy commit was rejected on push. This is not yet a mergeable release snapshot.

The current frontend build exposes `/`, `/analyze`, and `/api/live/[operation]`. The public Vercel entrypoint imports `cci.live_app`, which exposes only request-scoped live analysis and reports `storage=request_only`. The full `cci.main` API is a separate surface with candidate, job, pipeline, dossier, override, research, and live routers.

## What is already solid

- Live resume intake and analysis cap request bodies, repository selection, inspected file counts, and source-fetch time. The UI shows source receipts, evidence provenance, uncertainty, and unknown values. It says the result is technical decision support and not a hiring recommendation.
- The live API and web proxy use `Cache-Control: no-store`; the browser flow keeps the resume and result in page state and offers a user-initiated JSON export.
- The backend has SSRF and untrusted-code-execution checks in its CI workflow. The candidate repository is inspected as data; the analyzer does not execute candidate code.
- Verification rerun against the completed tasks' current shared checkout: `pnpm --filter web lint`, `pnpm --filter web build`, and `pnpm --filter web test` passed; Playwright reported 22 passing tests. `pytest -q` passed, with Starlette/httpx/AnyIO deprecation warnings. `pnpm audit --prod` reported no known JavaScript production vulnerabilities. The Compose YAML parsed, but Docker is not installed, so the stack could not be rendered or started. These checks cover the local checkout, not the production deployment.

These checks support implementation quality. They do not establish hiring accuracy, fair outcomes, tenant isolation, or production security.

## Launch blockers

| Priority | Finding | Evidence and consequence | Required gate |
| --- | --- | --- | --- |
| P0 | No end-user authentication or authorization on the full API. | `cci.main` mounts candidate, dossier, pipeline, override, and research routers without a global auth dependency. Candidate and dossier routes accept resource IDs directly. If the full API is reachable, a caller can list or retrieve candidate data and invoke changes without a verified user identity. | Integrate an identity provider. Derive user and organization from a verified server-side identity. Require role checks and resource-level authorization on every read and write route. |
| P0 | Organization scoping is optional and caller-controlled. | `GET /api/v1/candidates` accepts optional `organization_id`; the repository omits the organization filter when it is absent. The user model's organization field is not an authentication or membership check. | Remove client authority over organization IDs. Scope every query and mutation to the authenticated organization and add cross-tenant access tests, including exports, graphs, overrides, and job records. |
| P0 | The deployed live product and the full API are different products. | Vercel's `app.py` imports the stateless `live_app`; it does not deploy the workspace APIs. The current UI has no account, organization workspace, durable run history, or authenticated report route. The full API's pipeline state and dossier cache are process-local dictionaries. | Choose and document one production deployment path. Implement durable run execution and retrieval with database-backed state and a shared job system before selling persistent team workflows. |
| P1 | Demo candidate data must remain visibly synthetic and isolated from real people. | The audit remediation now replaces seeded candidate and recruiter identities, sample CV names/emails/employers/profile links, and the live DOCX test identity with demo values and reserved `.invalid` domains. Tests parse all five sample resumes and verify all six persisted seed records, contact domains, and source hosts. The public landing-page author byline is separate. These fabricated resumes and scores are for product illustration only and are not hiring evidence. | Keep demo identity and source data synthetic in future fixtures. Review historical Git revisions separately; this working-tree change does not rewrite prior commits. |
| P0 | Candidate data lifecycle is incomplete. | The live route is request-only and results disappear on refresh. The full API can persist candidate and dossier records but has no authenticated retention or deletion workflow connected to the product. The code does not provide a customer-configurable retention policy or complete candidate access/correction/deletion experience. | Define what is stored, for how long, where it is processed, and how customers and candidates exercise deletion, access, correction, and export rights. Connect those controls to actual storage and backups. |
| P0 | Hiring-use compliance and validity have not been established. | The product analyzes candidates for a hiring workflow. The UI disclaimer helps but cannot ensure that customers give the output meaningful human review. No independent, representative validation of job-related accuracy or disparate impact is present in the release evidence. | Set the intended use and sales jurisdictions. Obtain employment/privacy counsel review, independent validity and fairness assessment, human-review controls, candidate notice and correction paths, and documented limits before using live hiring data. |
| P1 | Open analysis endpoints have no account-level abuse controls. | Live intake and analysis are unauthenticated and have no application-level per-user rate limit, quota, or concurrency policy. Size and scan-time bounds reduce single-request cost but do not prevent repeated requests or denial-of-service spend. | Put the public service behind customer identity or an explicit controlled trial flow. Add edge and application rate limits, concurrency limits, quotas, abuse monitoring, and alerting. |
| P1 | Production still serves a different surface from the current checkout. | The public root redirects to `/analyze`. Live GET checks returned 200 for `/hr` (a hiring dashboard with an “Add Candidate” control and no sign-in text) and `/workspace` (a legacy shell). Both responses included `Access-Control-Allow-Origin: *` and lacked CSP and `X-Frame-Options`. The current local build emits only `/`, `/analyze`, and the live API route. The newer preview is behind Vercel Authentication; the Vercel deployment API returned 403 for this account scope, so project settings could not be inspected. | Identify the Vercel project and source commit for production; remove or protect legacy routes, set and verify production security headers and cross-origin policy, and only promote an audited, authenticated release tree. |
| P1 | The local Compose stack previously looked production-ready while exposing unsafe defaults. | It used a fixed database password, published database/cache/API/web ports on all interfaces, and set `APP_ENV=production` despite the full API lacking auth. This audit changed the stack to require a password, bind host ports to loopback, and declare development mode. | Keep Compose local-only. Create a separate production deployment with managed secrets, private database/cache networking, TLS, identity enforcement, and reviewed network policy. |
| P1 | The current checkout cannot be merged normally into the public GitHub main branch. | `git merge-base origin/main main` returned no commit. The scoped privacy change is committed locally as `aebee8e`; `git push origin main` was rejected as non-fast-forward. Other task changes remain uncommitted. The public Vercel project settings were not accessible for verifying which Git source it deploys. | Choose the release source of truth. Port the approved snapshot onto a branch based on `origin/main`, or intentionally migrate the repository. Do not force-push over public history without an explicit migration decision. |
| P1 | Enterprise operations are not evidenced. | The repo does not demonstrate a production SLO, alerting and incident workflow, tested backup restore, disaster recovery, production migration rollout, tenant audit review, or independent penetration test. | Complete an operational readiness review and publish the security and support materials required by target customers. |
| P1 | Supply-chain checks are incomplete. | The Node production dependency audit is clean, but backend dependency ranges use minimum versions without a committed Python lockfile, and CI has no Python dependency vulnerability scan or general static security scan. | Lock backend dependencies and add automated Python advisory and static security checks. Review and remediate findings continuously. |

## Hiring and privacy obligations

This is a jurisdiction-specific legal review item, not a certification conclusion. The European Commission's 3 August 2026 update says the AI Act generally applies from 2 August 2026 and that Annex III high-risk rules for employment will apply from 2 December 2027 following the AI Omnibus amendment. CandidateX needs a documented classification for its exact intended use and customer workflow before EU sales; the later application date is not a substitute for privacy, discrimination, or employment-law review. [AI Act, Annex III](https://eur-lex.europa.eu/legal-content/EN/TXT/?uri=CELEX%3A32024R1689), [European Commission implementation timeline](https://digital-strategy.ec.europa.eu/en/policies/regulatory-framework-ai).

If a customer uses the output as the sole basis for a decision with legal or similarly significant effects, GDPR Article 22 and associated safeguards may apply. Product copy alone does not control the customer's actual decision process. [GDPR, Article 22](https://eur-lex.europa.eu/legal-content/EN/TXT/?uri=CELEX%3A32016R0679).

## Changes made during this audit

- Set backend `DEBUG` to false by default and removed the built-in shared `SECRET_KEY` placeholder; added a regression test for those defaults.
- Changed the Compose stack to require `POSTGRES_PASSWORD`, bind published ports to `127.0.0.1`, and identify itself as development-only.
- Updated `.env.example` and the README to make the local-only boundary and password setup clear.
- Replaced candidate and recruiter identities in seed data and sample CVs with synthetic names, `.invalid` contacts and source URLs, and added a regression test for persisted seed data.

These changes reduce accidental exposure from the local integration stack. They do not implement authentication, tenant isolation, or a production deployment.

## Release gates before a company pilot

1. Resolve the disconnected Git histories and uncommitted task output; create one reviewed release snapshot on the chosen source branch and attach the audit build and tests to that exact commit.
2. Complete identity, role-based access, server-derived tenant scope, and cross-tenant isolation tests for every candidate-related route.
3. Select initial jurisdictions and intended-use limits; complete employment/privacy review, algorithmic validity and fairness review, and meaningful human oversight controls.
4. Ship durable jobs and reports only with documented retention, deletion, candidate rights, subprocessors, encryption, backup, and restore behavior.
5. Add production rate limits and quotas, metrics and alerts, dependency locking/scanning, a security review, and an accessibility review.

Until these gates pass, use synthetic data for demos. Do not describe the current checkout as a secure multi-tenant SaaS product or process live candidate data through the full API.
