**CandidateX frontend workflow audit — 28 September 2026**

The tested frontend has defects in authentication, candidate identity, job-description handling, persistence feedback, and recorded interview evaluations. These should be corrected before relying on the affected workflows for real candidate reviews. This report records findings; application fixes were outside this continuation's scope.

**Evidence and version scope.** Chromium ran against the isolated production preview at `http://127.0.0.1:3178`, build `8Tf6W5i3lvlo7H7aIkTvF`, from `C:\Users\yoray\AppData\Local\Temp\candidatex-frontend-audit-20260928-105715`. The 12 recovered browser scenarios completed, followed by three focused authentication/recovery scenarios. Their success means the diagnostic scenarios completed and reproduced the behavior described below; it does not mean the application passed regression tests. Ten additional route-handler probes used actual Next request/response classes and mocked OAuth responses, including negative and positive controls.

Application API mutations in browser workflow checks were intercepted. Uploads, outages, quota failures, delayed requests, and provider responses were controlled fixtures. No real OAuth account or backend candidate record was modified. The existing development servers were left running.

The workspace has no `.git` directory, so this audit cannot attribute findings to the last pushed commit or verify a production deployment. Source hashes and the comparison with the preview are preserved in [source-manifest.json](../../artifacts/frontend-audit-2026-09-28/source-manifest.json). Files changed concurrently during this continuation; consult the manifest and version notes rather than treating the preview as a moving copy of the workspace.

P1 indicates a security or data-integrity issue to address before relying on the affected feature. P2 indicates a functional issue to schedule next. P3 indicates a usability refinement. Findings refer to the tested snapshot; current-source qualifications appear at the end.

1. **F01 · P1 — Unsigned cookies establish an evaluator session.** [Session route](../../apps/web/app/api/auth/session/route.ts), lines 4–21; [client authentication](../../apps/web/lib/auth.ts), lines 13–51. A request with `cx_auth=audit%40example.invalid` returns an evaluator user with HTTP 200. A caller-supplied `cx_session` JSON object is also accepted, including `loginTime: 1`. Both were reproduced over HTTP, with an empty-cookie control returning `user: null`. The client also accepts locally supplied identity data. Use a server-validated session with integrity and expiry checks, and enforce authorization at protected data endpoints. This finding establishes identity forgery in the frontend/session endpoint; backend authorization was not tested end to end. Evidence: `http_forged_auth`, `http_forged_session`, and `auth-results.json`.

2. **F02 · P1 — OAuth state verification fails open.** [Callback route](../../apps/web/app/api/auth/callback/[provider]/route.ts), lines 32–44. Missing state, a missing state cookie, mismatched values, and matching malformed values all proceed to token exchange and session creation when the mocked provider accepts the code. A missing authorization code correctly prevents exchange. Reject all invalid state cases before contacting the provider and consume state once. Evidence: `oauth_missing_state`, `oauth_missing_state_cookie`, `oauth_mismatched_state`, and `oauth_malformed_matching_state`. Provider exchange was mocked; a real login-CSRF attack was not attempted.

3. **F03 · P2 — Login accepts external redirect destinations.** [Login client](../../apps/web/app/login/LoginClient.tsx), lines 99–103 and 165–166; [OAuth callback](../../apps/web/app/api/auth/callback/[provider]/route.ts), lines 161–162. Signing in with `redirect=https://audit-redirect.invalid/landing` navigates to that origin; the destination was intercepted locally. A matching OAuth state containing `//audit-redirect.invalid/landing` also produces an external Location header. Validate the normalized destination origin and permit only intended internal paths. Evidence: `login_external_redirect`, `oauth_external_redirect`. JavaScript execution through a redirect was not demonstrated and is excluded.

4. **F04 · P1 — Resume upload combines a new person with a sample identity.** [Candidate intake](../../apps/web/components/CandidateIntakeForm.tsx), lines 114–125, 186–197, and 221–230. After a fixture upload returns a new candidate ID and name with empty email/repository/skill fields, the UI changes the name but submits the sample ID `11111111-1111-1111-1111-111111111111`, two sample repositories, the sample email, and six sample skills. The upload never replaces the ID, and truthy/nonempty checks preserve old fields. Replace candidate state atomically from the new intake, including empty values and consent state. Evidence: `resume_old_data`, `resume_and_jd_pipeline`.

5. **F05 · P1 — A new analysis silently reuses the previous uploaded job description.** [Live evaluation](../../apps/web/components/evidence-os/LiveEvaluation.tsx), lines 306–325 and 412–438. Upload a text JD, complete a run, select “Run another analysis,” and upload another resume. The second form has no file card and an empty notes field, yet its analysis request contains the first run's JD. `newEvaluation()` clears visible fields but leaves `backendJdText` and `backendJobId`. Reset the entire JD state and invalidate outstanding uploads when starting another evaluation. Evidence: `new_run_jd_ui`, `new_run_jd_payload`.

6. **F06 · P1 — Workspace JD uploads are disconnected from parsing and analysis.** [Job intake](../../apps/web/components/JobIntakeForm.tsx), lines 64–77, 137–140, 303–304, and 333. The upload response's job ID is discarded. Subsequent parsing and pipeline requests use `jdText` and omit the uploaded `job_id`; the reproduction sent recruiter notes while the UI claimed the uploaded PDF was stored and ready. With no notes, the initialized template remains the input. The notes control also always displays an empty string after upload despite updating hidden state. Carry the uploaded document identity/text into extraction and analysis, and bind notes to their actual value. Evidence: `job_notes_control`, `failed_jd_parse`, `resume_and_jd_pipeline`.

7. **F07 · P1 — Failed requirement extraction displays default requirements as success.** [Job intake](../../apps/web/components/JobIntakeForm.tsx), lines 94–125 and 137–149. Return HTTP 503 from `/api/v1/jobs/parse`: the form still shows “Extracted Requirements (4)” containing initialized backend-role requirements and permits confirmation. The error is swallowed and `isExtracted` is set in `finally`. Show a failed extraction state and keep samples explicitly separate from parsed requirements. Evidence: `failed_jd_parse`.

8. **F08 · P1 — “Saved to HR” can mean neither storage path succeeded.** [Live evaluation](../../apps/web/components/evidence-os/LiveEvaluation.tsx), lines 356–382; [HR storage](../../apps/web/components/hr/hr-data.ts), `saveHRCandidate`. Force a localStorage quota exception and HTTP 503 for the backend save. The success message still appears, while the storage key remains absent. Local persistence swallows its exception, backend persistence is not awaited and swallows rejection, and the notice is unconditional. Report the actual outcome of each save and offer a retry/export when durability fails. Evidence: `failed_save_reported_success`.

9. **F09 · P1 — Untouched interview probes are recorded as completed ratings.** [Scorecard](../../apps/web/components/dossier/InterviewScorecardModal.tsx), lines 106, 133–138, and 193–217. Enter only an interviewer name and submit: all 12 probes are sent at 3/5, with generated “Evaluated probe…” notes and `lean_hire`. Initialize ratings/recommendation as unanswered and require explicit choices, or omit unrated probes. Evidence: `untouched_interview_payload`. The submission endpoint was intercepted; no real interview feedback was stored.

10. **F10 · P1 — Sign-out leaves saved candidate dossiers visible.** [Sign-out helper](../../apps/web/lib/auth.ts), lines 56–66; [HR storage](../../apps/web/components/hr/hr-data.ts), `HR_STORAGE_KEY` and `getSavedHRCandidates`; [HR page](../../apps/web/app/hr/page.tsx). After opening a saved candidate and signing out, the candidate remains in the origin-wide `cci_hr_saved_candidates` key and its View button remains usable on `/hr`. The HR page does not gate these records on identity. Scope locally saved data to the authenticated account and prevent guest/other-account access after sign-out. Evidence: `signout_retention`. This tests browser-local dossiers, not cross-tenant backend access.

11. **F11 · P2 — Failed Full Audit export silently becomes a short text summary.** [Dossier header](../../apps/web/components/dossier/DossierHeader.tsx), lines 73–106. With the export endpoint failing, “Download Full Audit (HTML)” downloads `audit_candidate_full_audit.html` containing 92 characters of Markdown: name, role, score, coverage, and an evidence count. It contains neither HTML nor the promised audit content. Preserve format and scope when a complete local fallback is available; otherwise report export failure. Evidence: `audit_html_fallback`. This finding concerns the full technical dossier's exporter; `lib/live-export.ts` has a separate implementation.

12. **F12 · P2 — Comparison exports the previous selection while loading.** [Candidate comparison](../../apps/web/components/CandidateComparison.tsx), lines 99–125 and 230–231. Load Alpha, select Beta, and hold Beta's response pending. Both candidates are selected, but Download Matrix stays enabled and the resulting file contains only Alpha. Bind exports to a completed selection version or disable them during loading. Evidence: `comparison_pending_export_enabled`, `comparison_pending_export_content`.

13. **F13 · P2 — Deleting a newly added draft leaves its row visible.** [HR dashboard](../../apps/web/components/hr/HRDashboard.tsx), draft state/merge and `onAdd`; [candidate quick view](../../apps/web/components/hr/CandidateQuickView.tsx), deletion handler. Add a local draft, open it, and confirm Delete draft. Storage is cleared and the modal closes, but the draft stays in the dashboard's separate `drafts` state and still appears in the table. Remove it from all active state collections and update the displayed result. Evidence: `deleted_draft_retained`. Candidate deletion code changed concurrently; see the version note below before applying this finding to current source.

14. **F14 · P2 — Analysis can start before JD extraction finishes.** [Role step](../../apps/web/components/evidence-os/RoleStep.tsx), lines 237–238; [analysis handler](../../apps/web/components/evidence-os/LiveEvaluation.tsx), lines 306–308. Hold `/api/live/parse-jd` pending: Continue remains enabled, and an analysis can be submitted with an empty JD and no job ID. Gate dependent steps on parsing completion and prevent a late response from changing another run's inputs. Evidence: `pending_jd_continue`, `pending_jd_analysis`.

15. **F15 · P2 — No conflict is presented as corroborated claims, even with no evidence.** [Dossier overview](../../apps/web/components/dossier/DossierOverviewTab.tsx), lines 75–77 and 155–187. A dossier with no evidence records, no claim corroboration results, and no capability conflicts displays “Claims Corroborated: No discrepancies…”. Absence of contradiction does not establish corroboration. Derive this notice from actual claim outcomes and show unavailable/unknown when evidence is absent. Evidence: `unknown_dossier_claims`.

16. **F16 · P2 — High scores override insufficient-evidence wording.** [Dossier overview](../../apps/web/components/dossier/DossierOverviewTab.tsx), lines 81–105; [dossier header](../../apps/web/components/dossier/DossierHeader.tsx), lines 117–129. A controlled dossier with RCI 95, coverage 2%, and `is_insufficient_evidence=true` receives an “Exceptional” tier and a broad positive executive assessment. The sparse-evidence warning elsewhere does not resolve the contradictory assessment. Score and sufficiency are independently computed by [the scoring module](../../services/backend/src/cci/scoring/rci.py), so a high score with low coverage is a supported condition. Make sufficiency constrain the displayed assessment. Evidence: `insufficient_high_score`.

17. **F17 · P2 — Weighted coverage is incorrectly converted into observed capability count.** [HR dashboard](../../apps/web/components/hr/HRDashboard.tsx), observed sorting and observed-count rendering. A candidate with coverage 0.86 and no cached dossier/count shows 10/12 observed in the table; opening the actual dossier shows 6/12. Role-weighted coverage is not a fraction of the twelve capabilities. Use the explicit count, compute it from available capability estimates, or display unknown. Evidence: `coverage_inferred_count`.

18. **F18 · P2 — Password recovery reports a dispatched token without sending a request.** [Login client](../../apps/web/app/login/LoginClient.tsx), lines 186–190 and 570–573. Submit the recovery form: success wording appears, but there are no application recovery requests. The handler only changes React state. Wire an actual recovery flow or accurately state its availability. The same modal also remains open after Escape. Evidence: `password_recovery_app_requests`, `forgot_escape`. The focused check filters unrelated antivirus-injected traffic.

19. **F19 · P2 — The remember-device checkbox does not affect persistence.** [Login client](../../apps/web/app/login/LoginClient.tsx), lines 60 and 148–152; [auth persistence](../../apps/web/lib/auth.ts), lines 47–51. Uncheck “Remember this device for 30 days” and sign in: identity is still stored in localStorage and `cx_auth` expires approximately 30 days later. Propagate the preference to session creation/storage. Evidence: `remember_unchecked`.

20. **F20 · P2 — Photo modal controls are blocked inside the dossier dialog, and keyboard focus stays outside.** [Photo lightbox](../../apps/web/components/ui/PhotoLightboxModal.tsx), lines 38–47 and 66–160; [modal wrapper](../../apps/web/components/ui/GlassModal.tsx), native `showModal()`. The photo is portaled into `document.body`, outside the native dialog's modal layer. In the full dossier, hit-testing its Close button returns the underlying DIALOG and a normal click times out. Separately, opening the lightbox from live results leaves focus outside it, including after Tab. Render the nested modal in the correct dialog layer and manage focus entry, containment, and restoration. Evidence: `nested_photo_hit`, `nested_photo_click`, `photo_focus_initial`, `photo_focus_tab`.

21. **F21 · P2 — Mobile navigation has no visible sign-out control.** [Platform header](../../apps/web/components/navigation/PlatformHeader.tsx), lines 100–112. At 390 pixels wide, the authenticated controls are hidden by `hidden md:flex`, and opening navigation reveals only route links. Provide account actions in the mobile menu. Evidence: `mobile_signout`.

22. **F22 · P3 — The mobile dossier requires substantial horizontal scrolling.** [Tab slider](../../apps/web/components/ui/TabSlider.tsx), lines 54 and 70; [dossier view](../../apps/web/components/dossier/DossierView.tsx), tab strip; [modal wrapper](../../apps/web/components/ui/GlassModal.tsx), scroll container. At 390 pixels viewport width, the 356-pixel dialog contains a scroll area approximately 827 pixels wide; the last tab starts around x=699. The page itself stays within the viewport, and the tab remains reachable by scrolling. Adapt the tab strip and header layout to narrow widths. Evidence: `mobile_dossier_ancestors`, `mobile_last_tab`, and [screenshot](../../artifacts/frontend-audit-2026-09-28/browser-results/audit-last-mobile-dossier--37176-sufficient-evidence-verdict/mobile-dossier.png).

**Additional verified wording issue.** A `.txt` JD is read with `file.text()` in the browser, yet its file card immediately says “Stored in backend” before any analysis/storage request. See `LiveEvaluation.tsx:193` and `RoleStep.tsx:154`; evidence: `text_jd_storage_claim`. The wording should describe what has actually completed.

**Version qualification.** At the first comparison, application sources matched the saved preview. The final comparison of 113 source/configuration files found additions in `components/hr/hr-data.ts` and `lib/api.ts`: candidate cleanup and DELETE helpers. Existing save/error-handling functions, deletion UI/state handling, and other cited code paths were unchanged. These additions do not resolve the reported findings in the inspected source. The audit did not invoke the deletion or cleanup helpers or rebuild the moving workspace. Exact differences and their impact are recorded in [version-notes.json](../../artifacts/frontend-audit-2026-09-28/version-notes.json).

**Limits.** This is a focused frontend workflow and authentication review, not a complete penetration test, backend audit, or accessibility conformance assessment. The current development server's earlier hydration problem was avoided using the isolated production build; its cause was not established. No finding claims JavaScript redirect execution, production exploitation, or verification against a pushed commit. A single early `forged_auth_cookie` UI observation logged `accessible: false` before the JD control settled; the later HTTP probes provide the session-forgery evidence.
