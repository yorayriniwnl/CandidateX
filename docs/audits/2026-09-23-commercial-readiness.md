# CandidateX Commercial Readiness Audit

- **Audit date:** 2026-09-23
- **Review tree:** `codex/candidatex-commercial-audit` in the isolated integration worktree
- **Inputs:** completed backend branch `codex/backend-hardening` (`dd57b03`) and Evidence OS branch `codex/candidatex-evidence-os` (`16fc361`)
**Decision:** **No-go for production hiring use or company sales as a multi-tenant SaaS.** The merged tree is a substantially improved technical demo, but it does not yet enforce account identity, organization isolation, or an auditable candidate-data lifecycle.

## Scope and limits

Reviewed the combined branch content, web routes and API clients, FastAPI routers, SQLAlchemy repository access, deployment and Compose configuration, sample data, CI/dependency posture, and available tests. The two task branches were combined in an isolated worktree and the conflict in `apps/web/tests/live-analysis.spec.ts` was resolved by retaining both branches' applicable assertions. The original checkout was left untouched. This is an internal code and configuration review, not a penetration test, legal opinion, algorithm validation, or security certification.

The source architecture has two materially different API paths. The Next.js live proxy forwards to `cci.live_app`, whose analysis path is request-scoped and reports `storage=request_only`; the larger `cci.main` app exposes database-backed candidate, job, dossier, pipeline, override, and research APIs. The build still includes the legacy `/hr` and `/workspace` pages. These paths do not form one authenticated company workspace.

The public Vercel site was checked on the audit date: `/` redirects to `/analyze`, which presents a request-only resume analysis flow. The Evidence OS interface in this review tree is not deployed there. This is a production snapshot, not proof about Vercel project settings or the separately hosted backend.

## Release blockers

| Priority | Finding | Evidence and impact | Required release gate |
| --- | --- | --- | --- |
| P0 | The API has no user authentication or authorization. | `services/backend/src/cci/main.py` mounts the candidate, dossier, job, pipeline, override, research, and live routers without an auth dependency. Candidate detail, dossier, graph, and export handlers accept resource IDs without checking the caller. If `cci.main` is reachable, an unauthenticated caller can read records or invoke mutations. | Integrate a maintained identity provider. Verify tokens server-side, enforce role and resource authorization on every protected route, and add anonymous-access and cross-user tests. |
| P0 | Organization scope is optional and caller-controlled. | Candidate and job list endpoints accept an optional `organization_id`; repository code omits the filter when it is absent. Override requests accept an organization UUID in the request body. Pipeline status, dossier, and export lookup use IDs without a server-derived organization check. | Derive organization membership from a verified identity and apply it to every query and mutation. Add cross-tenant tests for lists, details, exports, graphs, jobs, overrides, and run status. |
| P0 | Candidate data storage and retention are inconsistent across APIs. | The live route is intentionally request-only, while the full API can persist candidates, manifests, and dossiers in Postgres. The reviewed API/database source has no candidate deletion endpoint or retention/purge mechanism, and there is no complete access/correction workflow or demonstrated handling of backups and downstream copies. The public app and reviewed customer-facing docs have no privacy policy, DPA, subprocessor list, or privacy/security contact channel. | Choose the supported storage model; publish the privacy notice and contractual data terms; document subprocessors, retention, and deletion; implement and exercise candidate/customer rights against primary storage and backups. |
| P0 | Hiring validity, fairness, and intended-use controls are not established. | The product evaluates people for recruitment. The code and test suite do not establish representative job-related validity, disparate-impact performance, or meaningful human review in customer workflows. The current score is a weighted aggregation of observed evidence. Its confidence factors are explicitly described as relative weights, and source-family reliability starts from fixed Beta priors. The checked-in research generates synthetic candidates and observations; the README says the manuscript's reported rho cannot be reproduced because original per-seed outputs and exact calibration are unavailable. Cluster-bootstrap intervals quantify variation across observed evidence clusters, not prediction error against job performance. The Evidence OS UI does include limitations and says its probe order is not a hiring recommendation, but disclaimers do not establish validity or control customer use. | Set the initial use cases and sales jurisdictions; obtain employment/privacy counsel review; commission independent validation and fairness work against appropriate job-related outcomes; provide notice, correction, and meaningful human-review controls. |
| P1 | The live analysis service is anonymous and has no account quotas. | The live API bounds single request size and scan work, but does not enforce per-account rate limits, concurrency, or usage quotas. Repeated public requests can still consume service capacity and provider spend. | Require account identity for customer use and add edge plus application-level rate/concurrency limits, quotas, abuse monitoring, and alerting. |
| P1 | The full API is not a durable multi-worker job system. | Dossier and graph caches are process-local dictionaries, and pipeline state is held by the in-process pipeline service. The backend container starts two Uvicorn workers, so an analysis/status request can land on a different process and lose access to that state. | Store run state durably and use a shared job queue/cache; test retries, worker restarts, and multi-worker reads before promising team history. |
| P1 | The release boundary includes publicly reachable legacy prototype routes. | Both `/hr` and `/workspace` return HTTP 200 on the live Vercel site. `/hr` server-renders a hiring dashboard with an “Add Candidate” control and no sign-in gate in the rendered page; `/workspace` returns an initialization shell. This confirms public route reachability, but does not by itself prove that persisted candidate data is exposed through these pages. | Remove these routes from the company product or put them behind the same authenticated organization boundary; do not expose them as an accidental alternate workflow. |
| P1 | Production operations and release controls are not evidenced. | The repository has GitHub Actions CI for backend tests, frontend typecheck/build/browser tests, selected SSRF/scoring invariants, and a newly added Python package advisory job. It has no deployment job, secrets scan, Python static analysis, or deployed-site security scan. No reviewed production SLO, alert/incident process, tested backup restore, disaster recovery procedure, migration rollout, branch protection policy, or independent penetration test was provided. The local Compose file is not a production deployment. | Complete an operational readiness review and test monitoring, backups/restores, migration and rollback, incident response, and recovery objectives on the intended hosting stack. Verify branch protections and document the production deployment pipeline. |
| P1 | Python supply-chain controls remain incomplete. | CI now includes a pinned PyPA `pip-audit` action resolving the production dependency graph from `services/backend/pyproject.toml` under Python 3.12, but the GitHub job has not yet run. Python packages are still resolved from version ranges; there is no committed backend lockfile, and no Python static-analysis scan. A local `pip-audit` 2.10.1 run against the production dependency graph reported no known vulnerabilities on the audit date. | Lock the backend dependency graph, make production builds consume that lock, audit the locked runtime and development graphs, and add Python static analysis; retain scan results with releases. |
| P2 | Production browser security headers are incomplete. | The live `/analyze` response had HSTS and `Access-Control-Allow-Origin: *`, but lacked CSP, MIME-sniffing, frame, referrer, and permissions protections. The review tree now configures `nosniff`, `X-Frame-Options: DENY`, `strict-origin-when-cross-origin`, and a restrictive Permissions Policy, verified on the built `/analyze` response. CSP remains unresolved: the installed Next.js 16 guidance requires nonce CSP to use dynamic rendering, while the current pages are statically prerendered. The review-tree change is not deployed. The public HTML wildcard is not itself evidence of data exposure. | Choose a CSP/rendering policy that preserves the intended cache behavior, apply and verify it on the customer routes, then deploy and recheck production headers. Review cross-origin policy for HTML and API responses separately. |
| P2 (mitigated in review tree) | User persistence had an unsafe password-hash fallback. | `cci.db.repository.save_user` formerly defaulted `hashed_password` to the same literal `pbkdf2_sha256$insecure_dev_hash`, and the synthetic seeder and an integration test relied on it. The review tree now requires the caller to supply a value; demo/test accounts pass an explicit non-credential disabled marker, and a regression test rejects omission. No authentication endpoint exists, so this does not implement login or user authentication. | Keep demo/test markers unusable for authentication and align the user schema with the approved identity provider before adding account provisioning. |

## Hiring and privacy review

CandidateX is designed for a hiring workflow, so intended use and deployment jurisdiction need specialist review. The EU AI Act lists employment systems used for recruitment and selection in Annex III. The European Commission currently lists 2 December 2027 as the application date for relevant Annex III high-risk rules; that date does not replace present privacy, discrimination, or employment-law review. [AI Act, Annex III](https://eur-lex.europa.eu/legal-content/EN/TXT/?uri=CELEX%3A32024R1689) · [European Commission implementation timeline](https://digital-strategy.ec.europa.eu/en/policies/regulatory-framework-ai).

If a customer uses the output as the sole basis for a decision with legal or similarly significant effects, GDPR Article 22 and its safeguards may apply. Product copy does not determine whether a customer's actual decision is solely automated. [GDPR, Article 22](https://eur-lex.europa.eu/legal-content/EN/TXT/?uri=CELEX%3A32016R0679).

### What the score evidence establishes

The implementation estimates a role-weighted technical-evidence index from observed artifacts. The quality and ownership factors are deterministic model weights; `compute_evidence_confidence` explicitly states that they are not calibrated probabilities. `compute_source_reliability` uses fixed source-family priors unless verified true/false-positive counts are supplied. The intervals generated by the pipeline resample source clusters in a candidate's evidence.

Those mechanics and their invariant tests can support consistency and traceability claims. They do not show that a score predicts job performance, measures candidate potential fairly, or generalizes across populations, roles, and organizations. The committed research cohort is synthetic by construction, and the README says the reported manuscript result is not reproduced by the repository artifacts. Independent outcome-based validation is therefore a release blocker, not a claim that the current mathematical implementation is incorrect.

## Improvements made in this review tree

- Replaced candidate-like names, student emails, account handles, portfolio links, and repository links in web presets, HR sample data, seeded records, and sample resumes with clearly synthetic values and `.invalid` URLs. The sample resumes now say their profiles and claims are fictional. The intentional landing-page team attribution was retained.
- Changed the legacy intake confirmation to start unchecked and describe the submitter's responsibility to confirm that required notices or authorizations are in place. The application does not verify candidate consent or legal basis.
- Disabled backend debug mode by default and removed the built-in shared secret value. Added a regression test for both defaults.
- Hardened the local-only Compose stack: requires a supplied database password, binds published ports to loopback, sets development mode with debug disabled, and configures the web container to reach the backend by its service name. Updated `.env.example` and the README to label the stack local-only and warn against live hiring data.
- Added `nosniff`, frame denial, a strict referrer policy, and a restrictive Permissions Policy to Next responses. Added a Playwright regression test for the `/analyze` response headers. A nonce CSP is still open because the current static page rendering strategy and Next.js nonce requirements need a cache/rendering decision.
- Removed the shared insecure password-hash default from `save_user`; synthetic seed accounts and the DB test now pass an explicit disabled marker. Added a regression test requiring an explicit hash value.
- Added a Python dependency advisory job to GitHub Actions, using the official PyPA `pip-audit` action pinned to its verified v1.1.0 commit and scanning the backend production dependency graph under Python 3.12.

These changes reduce accidental exposure and improve demo hygiene. They do not add sign-in, tenant isolation, durable job state, or production controls.

## Gates before a company pilot

1. Select and configure the identity provider, then implement server-verified login, organization membership, role checks, and cross-tenant isolation throughout the API.
2. Define the supported data model and implement retention, deletion, candidate access/correction/export, encryption, backups, and operational ownership.
3. Define intended use and launch jurisdictions; complete legal review, independent job-related validity and fairness testing, and human-review/candidate-correction controls.
4. Replace process-local run state with durable jobs and shared state if customer history or team workflows are promised; otherwise remove the persistent API surfaces from the supported production product.
5. Add per-account abuse controls, locked dependency builds, Python static/dependency scans, production monitoring, backup recovery evidence, accessibility review, and an independent security assessment.

Until those gates pass, restrict the product to synthetic-data demonstrations. Do not market the current tree as a secure multi-tenant SaaS or use it for live hiring decisions.
